# บท 014: ถามหลายคำถามพร้อมกันด้วย batch

ถ้ามี 100 คำถามที่ต้องถามโมเดล การถามทีละข้อใช้เวลานานมาก แต่ถ้ายิงทั้ง 100 ข้อพร้อมกันก็เสี่ยงชนลิมิตของ provider บทนี้เรียนวิธีถามหลายข้อด้วย `.batch()` และควบคุมจำนวนงานพร้อมกันด้วย `maxConcurrency` ใช้เวลาประมาณ 45-60 นาที ทำทั้งแบบ Ollama (`.ollama.ts`) และ Google (`.google.ts`)

## จบบทนี้แล้วทำอะไรได้

- ถามหลายคำถามในครั้งเดียวด้วย `model.batch(questions)`
- อธิบายได้ว่า "พร้อมกันมากเกินไป" ทำให้เจอ 429 ได้อย่างไร และแก้ด้วย `maxConcurrency`
- เขียนตัวจำกัดงานพร้อมกันเองได้ (เพื่อเข้าใจว่า `maxConcurrency` ทำอะไร)
- นับจำนวนงานพร้อมกันจริงด้วย callback ของโมเดล
- ใช้ `returnExceptions` ให้ batch ไม่ล้มทั้งชุดเมื่อบางข้อล้ม
- เลือก `maxConcurrency` ที่เหมาะกับลิมิตของ provider

## เชื่อมกับที่รู้แล้ว

| ที่รู้แล้ว | ในบทนี้ |
|---|---|
| TypeScript: `Promise.all` รัน Promise หลายตัวพร้อมกัน | `.batch()` ทำแบบเดียวกัน แต่คุมจำนวนพร้อมกันได้ |
| บท 013: 429 คือโควต้าเต็ม ต้องรอแล้วลองใหม่ | ลดโอกาสเจอ 429 ตั้งแต่ต้นด้วยการไม่ยิงพร้อมกันเกินไป |
| บท 012: error มีชนิดและ status | `returnExceptions` ให้ error อยู่ในอาร์เรย์ผลแทนการ throw |
| บท 007: `model.invoke(q)` ถามทีละข้อ | `model.batch([q1, q2, ...])` ถามหลายข้อ ได้คำตอบเรียงตามคำถาม |

## เนื้อหา

### 1. `.batch()` ถามหลายข้อพร้อมกัน

```ts
const answers = await model.batch(["คำถาม 1", "คำถาม 2", "คำถาม 3"]);
// answers[0] คือคำตอบของคำถาม 1, answers[1] ของคำถาม 2 ... เรียงตามคำถามเสมอ
```

แม้งานจะเสร็จไม่พร้อมกัน ผลที่ได้เรียงตามลำดับคำถามเสมอ

### 2. ทำไมต้องจำกัดงานพร้อมกัน

ทุก provider คุมอัตราการเรียก เรียกพร้อมกันจำนวนมากเสี่ยงโดน 429 (บท 013) หรือทำให้เซิร์ฟเวอร์ตอบช้า ทางแก้คือบอกว่าให้ทำพร้อมกันไม่เกินกี่งาน:

```ts
await model.batch(questions, { maxConcurrency: 2 });
```

ถ้ามี 5 คำถามและ `maxConcurrency: 2` จะเริ่ม 2 ข้อแรกก่อน ข้อไหนเสร็จก็หยิบข้อถัดไปมาทำ ไม่มีช่วงใดที่ทำเกิน 2 ข้อ

ลิมิตของ provider ในบทนี้ยังไม่ได้ยืนยันด้วยตัวเลขจริง: ลิมิตของแผนฟรี Gemini และลิมิตงานพร้อมกันของ Ollama Cloud TODO(6b): ตัวเลขจริง ตอนเรียนควรเริ่มจากค่าน้อยก่อน (1-3) แล้วค่อยเพิ่มเมื่อแน่ใจว่าไม่ชนลิมิต

### 3. ขั้นที่ 1: เขียนตัวจำกัดงานพร้อมกันเอง

```ts
async function runLimited<T>(tasks: (() => Promise<T>)[], limit: number): Promise<{ results: T[]; peak: number }>
```

- `tasks` คือรายการ "ฟังก์ชันที่ยังไม่ได้เรียก" แต่ละตัวเมื่อเรียกจะเริ่มงานและคืน Promise (ถ้าเรียกเลยตอนสร้างรายการ งานจะเริ่มพร้อมกันหมดโดยเราคุมไม่ได้)
- เปิด "worker" `limit` ตัว แต่ละตัววนหยิบงานถัดไปจากรายการจนหมด จึงมีงานพร้อมกันไม่เกิน `limit`
- เก็บผลลงตำแหน่งเดิมของงาน (`results[index]`) ผลจึงเรียงตามลำดับงานแม้งานเสร็จไม่พร้อมกัน
- `peak` คือจำนวนงานพร้อมกันสูงสุดที่เคยเกิดขึ้นจริง
- ไฟล์ตัวอย่างทดลองกับงานปลอม 5 งานที่รอ 50, 10, 30, 20, 40 ms (ไม่ยิงเน็ต) 2 รอบ: `limit` 5 (ไม่จำกัด) และ `limit` 2

### 4. ขั้นที่ 2: `model.batch` กับ `maxConcurrency` และ tracker

ถาม 5 คำถามเรื่องสินค้าของ DN Shop (ทุกข้อลงท้าย `ตอบไม่เกิน 1 ประโยค`) ด้วย `model.batch(qs, { maxConcurrency: 2, callbacks: [tracker] })`

`tracker` คือ object ที่ฟังเหตุการณ์ของโมเดล เพื่อนับงานที่กำลังทำอยู่:

```ts
const tracker = {
  handleChatModelStart: () => { active += 1; peak = Math.max(peak, active); },
  handleLLMEnd: () => { active -= 1; },
  handleLLMError: () => { active -= 1; },
};
```

- `handleChatModelStart` ถูกเรียกตอนเริ่มเรียกโมเดลแต่ละครั้ง (+1)
- `handleLLMEnd` ถูกเรียกตอนโมเดลตอบเสร็จ และ `handleLLMError` ตอนล้ม (-1 ทั้งคู่ ไม่เช่นนั้นตัวนับจะค้าง)
- `peak` จดค่า `active` ที่สูงสุดที่เคยเห็น นั่นคือ "งานพร้อมกันสูงสุด"
- ตัวเลขนี้อาจน้อยกว่า `maxConcurrency` ได้ ถ้าคำตอบเสร็จเหลื่อมกันพอดี แต่จะไม่เกินเด็ดขาด

### 5. `returnExceptions`: บางข้อล้มไม่ต้องล้มทั้งชุด

ปกติ ถ้ามีข้อใดข้อหนึ่งล้ม `batch` จะ throw ทั้งชุดและผลของข้ออื่นหายไป ถ้าส่ง `returnExceptions: true` ข้อที่ล้มจะกลายเป็นค่า `Error` อยู่ในอาร์เรย์ผลแทน (ผลเป็น `(string | Error)[]`) ข้ออื่นยังได้คำตอบปกติ

```ts
const results = await runnable.batch(questions, { maxConcurrency: 2 }, { returnExceptions: true });
```

สังเกตตำแหน่ง: `maxConcurrency` อยู่ในอาร์กิวเมนต์ที่ 2 (config) ส่วน `returnExceptions` อยู่ในอาร์กิวเมนต์ที่ **3** ถ้าใส่ผิดตำแหน่ง โปรแกรมจะไม่ทำงานตามที่ตั้งใจ

`.batch()` ใช้ได้กับ `RunnableLambda` ด้วย แบบฝึกข้อ 1 ใช้ `RunnableLambda` ที่ตั้งใจ throw เมื่อคำถามมี `(ทดสอบล้ม)` เพื่อจำลองข้อที่ล้ม โดยไม่ต้องรอให้โมเดลล้มจริง

### 6. เลือก `maxConcurrency`

| ค่า | ข้อดี | ข้อเสีย |
|---|---|---|
| 1 | ปลอดภัยที่สุด ไม่ชนลิมิต | ช้าที่สุด (เท่ากับถามทีละข้อ) |
| 2-3 | เร็วขึ้นประมาณ 2-3 เท่า ยังเสี่ยงต่ำ | ถ้าลิมิตของแผนเข้มมาก อาจยังชนได้ |
| สูงกว่านี้ | เร็วมากถ้า provider รับไหว | เสี่ยง 429 และ error ชั่วคราวมากขึ้น (บทนี้ไม่ให้เลือก) |

Ollama ในเครื่องใช้ GPU ของเครื่องเราเอง มักประมวลผลได้ทีละไม่กี่งาน (ขึ้นกับเครื่อง) ค่าสูงจึงอาจไม่ช่วยให้เร็วขึ้น ส่วน Gemini แผนฟรีและ Ollama Cloud มีลิมิตของ provider แบบข้างบน

## จุดที่มักพลาด

- **ยิงพร้อมกันทั้งหมดแล้วเจอ 429:** แก้ด้วย `maxConcurrency` และลองใหม่ตามบท 013 อย่าคาดว่าจะเจอ 429 ทุกครั้ง ขึ้นกับแผนและช่วงเวลา บทนี้ไม่ได้ออกแบบให้ทำให้เกิด 429
- **ใส่ `returnExceptions` ในอาร์กิวเมนต์ที่ 2:** ต้องเป็นอาร์กิวเมนต์ที่ 3 (`batch(xs, config, { returnExceptions: true })`)
- **ลืมลบตัวนับตอนล้ม:** tracker ต้องลด `active` ทั้งตอนจบ (`handleLLMEnd`) และตอนล้ม (`handleLLMError`) ไม่เช่นนั้นค่าสูงสุดจะเพี้ยน
- **ใส่งานที่เรียกแล้วลงใน `tasks`:** `tasks` ต้องเป็นฟังก์ชันที่ยังไม่ถูกเรียก (`() => ask(q)`) ไม่ใช่ Promise (`ask(q)`)
- **คิดว่าผลเรียงตามเวลาที่เสร็จ:** ผลของ `batch` เรียงตามลำดับคำถามเสมอ
- **ตั้ง `maxConcurrency` สูงเพราะอยากเร็ว:** เร็วขึ้นไม่เท่าตัว และเสี่ยงชนลิมิต เริ่มจากน้อยก่อน

**`exercise-1.*`**


- [ ] มีบรรทัด `ข้อ 1:` ถึง `ข้อ 5:` ตามลำดับ แต่ละข้อเป็น `สำเร็จ` หรือ `ล้มเหลว (ข้อความ)` ที่มีข้อความจริง
- [ ] บรรทัดสุดท้าย `สำเร็จ X ล้มเหลว Y` มี X + Y = 5 และ X, Y มากกว่า 0
- [ ] X และ Y ตรงกับจำนวนข้อที่สำเร็จและล้มเหลวในบรรทัดรายข้อ
