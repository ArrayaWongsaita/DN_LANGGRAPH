# บท 022 ⭐: เมื่อโมเดลตอบไม่ตรง schema

บท 021 สอนให้ `withStructuredOutput` แปลงคำตอบของโมเดลเป็น object ตาม schema และบอกว่ามีสองกรณีที่ไม่สำเร็จ: โมเดลไม่เรียกเครื่องมือ (`undefined`) กับ args ไม่ตรง schema (`OutputParserException`) บทนี้เปิดดูด้านหลังของทั้งสองกรณีด้วย `includeRaw` ว่าโมเดลส่งอะไรมาจริง ๆ แล้วเขียนโค้ดให้เดินต่อได้โดยไม่พัง ก่อนจบช่วงที่ 3 ด้วยแชทบอทที่แยกประเภทคำถามก่อนตอบ ใช้เวลาประมาณ 60-90 นาที ทำทั้งแบบ Ollama (`.ollama.ts`) และ Google (`.google.ts`)

## จบบทนี้แล้วทำอะไรได้

- บอกได้ 3 แบบที่ทำให้ args ของโมเดลใช้ไม่ได้: ไม่เรียกเครื่องมือ, enum ผิด, ขาดหรือผิด type
- ตรวจ args ที่สงสัยด้วย `CustomerQuestion.safeParse` แล้วอ่าน `z.prettifyError` ให้รู้ว่าผิดที่ field ไหน
- ใช้ `includeRaw: true` อ่าน `{ raw, parsed }` โดยไม่ต้อง `try/catch` และแยกได้ว่า `parsed` เป็น `null` หรือ `undefined`
- อ่าน `raw.tool_calls` เพื่อดู args ที่โมเดลส่งมาจริง แล้วเขียนฟังก์ชันอธิบายเหตุผลเป็นภาษาไทยบรรทัดเดียว
- ลองแปลงซ้ำเมื่อได้ `null` ด้วย `classifyWithRetry` และรู้ว่าเมื่อไรควรเลิกลอง
- ประกอบแชทบอทที่แยกประเภทคำถามก่อนตอบ และใส่ข้อมูลร้านเฉพาะที่ตรงกับคำถาม โดยรหัสลูกค้ามาจากระบบเท่านั้น

## เนื้อหา

บทนี้ต้องผ่านบท 021 ก่อน

### 1. args ใช้ไม่ได้ได้ 3 แบบ

`withStructuredOutput` ไม่ได้รับประกันว่าได้ object ที่ใช้ได้ทุกครั้ง ปัญหาเกิดได้ 3 แบบ:

| แบบ | เกิดเมื่อ | ตรวจพบด้วย |
|---|---|---|
| ไม่เรียกเครื่องมือ | โมเดลตอบเป็นข้อความธรรมดา (Ollama บังคับเรียกเครื่องมือไม่ได้) | `parsed` เป็น `undefined` |
| enum ผิด | โมเดลเลือกค่านอกลิสต์ เช่น `"shipping"` แทน `"policy"` | `safeParse` ไม่ผ่านที่ field นั้น |
| ขาดหรือผิด type | ไม่ส่ง field ที่บังคับ หรือส่ง `"urgent": "yes"` แทน `true` | `safeParse` ไม่ผ่านที่ field นั้น |

ขั้นที่ 1 ของไฟล์จำลองด้วย args ปลอม 3 ก้อน (ไม่ยิงเน็ต) ผลเหมือนกันทุกเครื่อง:

```
--- ขั้นที่ 1: args ที่โมเดลอาจส่งมา (ข้อมูลปลอม) ---
args ที่ 1: {"category":"order","keywords":[],"orderId":"O1002","urgent":true,"summary":"ถามสถานะคำสั่งซื้อ"}
  ผ่าน → ประเภท order
args ที่ 2: {"category":"shipping","keywords":[],"urgent":false,"summary":"ถามค่าส่ง"}
  ไม่ผ่าน
  ✖ ตัวเลือกไม่ถูกต้อง: ควรเป็นหนึ่งใน "product"|"order"|"policy"|"other"
    → at category
args ที่ 3: {"category":"product","keywords":["แก้ว"],"summary":"ถามเรื่องแก้ว"}
  ไม่ผ่าน
  ✖ ประเภทข้อมูลไม่ถูกต้อง: ควรเป็น boolean แต่ได้รับ undefined
    → at urgent
```

`z.prettifyError` บอกถึงระดับ field (`→ at category`, `→ at urgent`) ซึ่งเป็นประโยชน์ตอนเขียน log: ผู้อ่านรู้ทันทีว่าต้องแก้ prompt ตรงไหน ไม่ต้องเดาจากข้อความยาว ๆ ของ zod

### 2. `includeRaw` คืน `{ raw, parsed }` และไม่ throw

```ts
const chain = model.withStructuredOutput(CustomerQuestion, { name: "classify_question", method: "functionCalling", includeRaw: true });
const { raw, parsed } = await chain.invoke(messages);
```

- `parsed` เป็น args ที่ผ่าน schema แล้ว หรือ `null`/`undefined` เมื่อไม่ผ่าน **โดยไม่ throw** (ต่างจากตอนไม่ใส่ `includeRaw` ที่ได้ `OutputParserException`)
- `null` เกิดเมื่อโมเดลเรียกเครื่องมือแต่ args ไม่ผ่าน schema, `undefined` เกิดเมื่อโมเดลไม่ได้เรียกเครื่องมือเลย สองค่านี้แยกความหมาย แต่โค้ดส่วนใหญ่ไม่ต้องแยก: ตรวจ `parsed == null` ครั้งเดียวพอ (ถ้าใช้ `=== null` จะพลาดกรณี `undefined`)
- `raw` คือ `AIMessage` ตัวจริงที่โมเดลส่งมา ใช้ดูต่อได้ว่ามันส่งอะไรมาจึงไม่ผ่าน

ไฟล์ `.ollama.ts` ส่ง `method: "functionCalling"` เพราะ Ollama Cloud ไม่รับ schema ทาง `format` ส่วน `.google.ts` ส่งแค่ `{ name: "classify_question" }` เพราะ `ChatGoogle` ใช้ `functionCalling` ที่บังคับเรียกเครื่องมือเป็นค่าเริ่มต้น

### 3. `raw.tool_calls` บอกว่าโมเดลส่ง args อะไรมาจริง ๆ

`raw.text` เป็นข้อความว่างเมื่อโมเดลเรียกเครื่องมือ (args ไปอยู่ใน `raw.tool_calls`) และมีข้อความเมื่อโมเดลตอบเป็นคำพูด ตัวช่วย `rawSummary(raw)` ใน `customer-question.ts` รวมสองกรณีเป็นบรรทัดเดียว:

```ts
export function rawSummary(raw: BaseMessage): string {
  const call = AIMessage.isInstance(raw) ? raw.tool_calls?.[0] : undefined;
  return oneLine(call === undefined ? raw.text : JSON.stringify(call.args), 120);
}
```

ขั้นที่ 2 ของไฟล์ใช้ตัวนี้พิมพ์ `  คำตอบดิบ: …` เมื่อเจอ `parsed == null` แล้วจึงไปข้อถัดไป: ทั้งไฟล์ไม่มี `try/catch` และไม่มี stack trace หลุดออกมา เพราะ `includeRaw` ไม่ throw ตั้งแต่แรก

### 4. ขั้นที่ 2: แยกประเภทคำถามจริง 6 ข้อ

ขั้นที่ 2 ถาม `MESSAGES` 6 ข้อ โดย system คือ `CLASSIFY_SYSTEM` (`จัดประเภทคำถามของลูกค้าร้าน DN Shop แล้วตอบโดยเรียกเครื่องมือ classify_question เท่านั้น`) แต่ละข้อพิมพ์อย่างใดอย่างหนึ่ง:

```
ข้อ 2: order | orderId: O1002 | ด่วน: ใช่ | ลูกค้าถามสถานะคำสั่งซื้อ O1002 และรอนานมาก
  สถานะคำสั่งซื้อ O1002: กำลังจัดส่ง
```

หรือ

```
ข้อ 5: แปลงไม่สำเร็จ
  คำตอบดิบ: {"category":"food"}
```

แล้วสรุป `แปลงสำเร็จ: N/6` กับ `นับตามประเภท: product A · order B · policy C · other D` (พิมพ์ครบทั้ง 4 ประเภท แม้เป็น 0)

**เรียกทีละข้อ ไม่ใช้ `.batch`:** ไฟล์เรียก `chain.invoke` ทีละข้อความ เพราะ `includeRaw` ทำงานด้วย `withFallbacks` ซึ่ง fallback **ทั้ง batch**: ถ้าใช้ `.batch` แล้วมีข้อเดียว args ไม่ผ่าน ทุกข้อจะได้ `parsed` เป็น `null` หมด (ทดสอบบน opencode shim แล้ว) เมื่อต้องการรู้ว่าข้อไหนผิดจึงต้องเรียกแยกทีละข้อ ถ้าไม่ต้องใช้ `includeRaw` (ไม่ต้องรู้ว่าข้อไหนผิด) จะใช้ `.batch` กับ `maxConcurrency` ตามบท 014 เพื่อให้เร็วขึ้นก็ได้

### 5. แยกประเภทเป็น object แล้วโค้ดเลือกทางต่อได้

คำถามของลูกค้าแต่ละประเภทต้องใช้ข้อมูลคนละชุด: ถามสินค้าต้องค้นสินค้า ถามคำสั่งซื้อต้องเปิดคำสั่งซื้อ ถามกฎร้านไม่ต้องเปิดอะไรเลย การให้โมเดลตอบเป็น `CustomerQuestion` (object) ทำให้โค้ด `if (question.category === "order")` เลือกทางต่อได้ ส่วนการให้โมเดลตอบเป็นข้อความอิสระทำแบบนี้ไม่ได้เพราะต้องเดาจากถ้อยคำ ในบทหลัง ๆ (graph) ทางเลือกนี้จะกลายเป็น **router** ที่เลือกโหนดถัดไป

### 6. รหัสลูกค้ามาจากระบบ ไม่ใช่จากโมเดล

`CUSTOMER_ID = "C001"` เป็นค่าที่ระบบได้จากการ login ไม่อยู่ใน schema และโมเดลไม่มีทางเปลี่ยนได้ ถ้าปล่อยให้โมเดลบอกว่า "ดูลูกค้าคนไหน" มันก็ขอดูคำสั่งซื้อของคนอื่นได้

`getOrder(orderId, customerId)` จึงตรวจเจ้าของทุกครั้ง และตอบ **เหมือนกันทั้งสองกรณี** เมื่อไม่เจอ: คำสั่งซื้อที่ไม่มีอยู่จริง กับคำสั่งซื้อของลูกค้าคนอื่น ตัวอย่างเช่น `O1004` เป็นของ `C002` แต่เมื่อ `C001` ถาม ระบบตอบ `ไม่พบคำสั่งซื้อ O1004 ของลูกค้ารายนี้` เหมือนคำสั่งซื้อที่ไม่มีอยู่ ถ้าตอบต่างกัน ผู้ใช้จะเดาเลขคำสั่งซื้อของคนอื่นได้ว่ามีอยู่จริง

### 7. แบบฝึกหัด 3 รวมบท 016-022 เข้าด้วยกันอย่างไร

| บท | ชิ้นที่หยิบมาใช้ |
|---|---|
| 016 | loop `ask()` + `history` + `model.stream()` + พิมพ์ `ลาก่อนครับ` เมื่อจบ |
| 017 | system prompt 4 ส่วน (บทบาท ขอบเขต น้ำเสียง สิ่งที่ห้ามตอบ) |
| 018 | ข้อมูลร้านใน prompt แต่ใส่เฉพาะที่ `contextFor` ประกอบให้ตามประเภทคำถาม |
| 019 | วัดผลด้วยตัวเลขสรุป (`แปลงสำเร็จ: N/6`) ที่นับจากบรรทัดรายข้อ ไม่ใช่พิมพ์ค่าคงที่ |
| 020 | ตรวจ args ด้วย zod (`safeParse` เท่านั้น) และพิมพ์เหตุผลเป็นภาษาไทย |
| 021 | `withStructuredOutput` กับ `classify_question` |
| 022 | `includeRaw` เพื่อรู้ว่าแปลงไม่ผ่านเพราะอะไร |

ทุกตาของแชททำ 4 อย่างตามลำดับ: แยกประเภทคำถาม (`includeRaw`) → `contextFor` ประกอบข้อมูลจากร้าน → ใส่ข้อมูลนั้นใน system ใต้หัวข้อ `## ข้อมูลจากระบบร้าน` (ว่างให้ใส่ `ไม่มี`) → stream คำตอบ ไฟล์พิมพ์ประเภทและข้อมูลที่ส่งให้โมเดลก่อนคำตอบทุกตา เพื่อให้ตรวจย้อนหลังได้ว่าตอบผิดเพราะข้อมูลที่ให้ผิดหรือเพราะโมเดลเอง

### 8. วิธีออกจากแชทของแบบฝึกหัด 3

| วิธี | ผล |
|---|---|
| พิมพ์ `จบ` แล้ว Enter | ใช้ได้ทุกระบบ เป็นวิธีหลักที่แนะนำ |
| กด Ctrl+D (macOS/Linux) | input หมด `ask()` คืน `null` โปรแกรมจบเองและพิมพ์ `ลาก่อนครับ` |

## จุดที่มักพลาด

- **ลืมว่า `parsed` เป็น `null`/`undefined` ได้:** type ของ `withStructuredOutput` บอกว่าได้ object แต่ค่าจริงเป็น `null` ได้เสมอเมื่อใส่ `includeRaw` ต้องตรวจ `parsed == null` ก่อนใช้ทุกครั้ง
- **ใช้ `=== null`:** พลาดกรณีที่โมเดลไม่ได้เรียกเครื่องมือ (`undefined`) ใช้ `== null` ครอบทั้งสองค่า
- **ใช้ `.batch` กับ `includeRaw` แล้วหวัง `parsed` รายข้อ:** `withFallbacks` ของ `includeRaw` fallback ทั้ง batch ถ้ามีข้อเดียวไม่ผ่าน ทุกข้อจะได้ `parsed` เป็น `null` (ทดสอบบน shim แล้ว) ต้องเรียกทีละข้อถ้าอยากรู้ว่าข้อไหนผิด
- **ใช้ `.batch` โดยไม่จำกัด `maxConcurrency`:** ยิงพร้อมกันหมด เสี่ยง 429 (บท 014)
- **ปล่อยให้ stack trace ขึ้นจอ:** `withStructuredOutput` แบบไม่ใส่ `includeRaw` throw `OutputParserException` ถ้าไม่จับ โปรแกรมจะหยุดทั้งไฟล์และผู้ใช้เห็น stack trace แทนเหตุผลภาษาไทย
- **ให้โมเดลเป็นคนบอกว่าดูคำสั่งซื้อของใคร:** รหัสลูกค้าต้องมาจากระบบ (`CUSTOMER_ID`) แล้วให้ `getOrder(id, customerId)` ตรวจเจ้าของเสมอ ไม่งั้นผู้ใช้เดารหัสคำสั่งซื้อของคนอื่นได้
- **บอก "ไม่พบ" ต่างจาก "ไม่มีสิทธิ์":** สองกรณีนี้ต้องตอบเหมือนกัน ไม่งั้นเท่ากับยืนยันว่าคำสั่งซื้อนั้นมีอยู่จริง
- **ลืม `.describe()` ใน schema:** `keywords` ที่ไม่มีคำอธิบายจะได้คำกว้าง ๆ อย่าง `["กาแฟ"]` ทำให้ค้นได้ผลเยอะเกินจนข้อมูลที่ใส่ prompt ยาวโดยไม่จำเป็น
- **ใส่ชื่อโมเดลในโค้ด:** อ่านจาก `.env` ผ่าน `env()` เหมือนทุกบท

### ขั้นที่ 2 และแบบฝึกหัด: เทียบกับ checklist

ตัวอย่างผลของ `example.*` (ข้อความสรุปของโมเดลต่างกันได้ ตัวเลขและบรรทัดที่ไฟล์พิมพ์เองต้องตรง):

```
--- ขั้นที่ 2: แยกประเภทคำถามจริง 6 ข้อ (includeRaw) ---
ข้อ 1: product | orderId: - | ด่วน: ไม่ | ลูกค้าถามว่าทางร้านมีเมล็ดกาแฟคั่วอ่อนจำหน่ายหรือไม่
ข้อ 2: order | orderId: O1002 | ด่วน: ใช่ | ลูกค้าถามสถานะคำสั่งซื้อ O1002 และรอนานมาก
  สถานะคำสั่งซื้อ O1002: กำลังจัดส่ง
...
แปลงสำเร็จ: 6/6
นับตามประเภท: product 2 · order 2 · policy 1 · other 1
```

**`example.ollama` และ `example.google`**
- [ ] มีหัวข้อ `args ที่ 1`, `args ที่ 2`, `args ที่ 3` ตามลำดับ
- [ ] args ที่ 1 ตามด้วยบรรทัด `ผ่าน → ประเภท order`
- [ ] args ที่ 2 (enum ผิด) มีบรรทัด `→ at category`
- [ ] args ที่ 3 (ขาด `urgent`) มีบรรทัด `→ at urgent`
- [ ] ขั้นที่ 2 มีบรรทัดของข้อ 1 ถึงข้อ 6 ครบ ข้อละ 1 บรรทัด (เป็น `ข้อ i: <category> | orderId: … | ด่วน: … | …` หรือ `ข้อ i: แปลงไม่สำเร็จ` + `  คำตอบดิบ: …`)
- [ ] `แปลงสำเร็จ: N/6` โดย N อย่างน้อย 5 และเท่ากับจำนวนบรรทัด `ข้อ i: <category> | orderId: …`
- [ ] `นับตามประเภท` มีครบ 4 ประเภท (`product`, `order`, `policy`, `other`) และผลรวมเท่ากับ N
- [ ] ข้อ 2 แปลงสำเร็จเป็น `order` ของ `O1002` และมีบรรทัด `สถานะคำสั่งซื้อ O1002: กำลังจัดส่ง`
- [ ] ทุกบรรทัด `สถานะคำสั่งซื้อ <id>: <ป้าย>` ใช้ป้ายที่ `getOrder(<id>, "C001")` คืนมา และคำสั่งซื้อของลูกค้าคนอื่น (เช่น `O1004`) ต้องได้ `ไม่พบคำสั่งซื้อ <id> ของลูกค้ารายนี้` ไม่ใช่สถานะจริง

**`exercise-1.*`**

```
ตรวจตัวอย่าง 1: ไม่ได้เรียกเครื่องมือ ตอบเป็นข้อความ: ขอโทษครับ ผมไม่แน่ใจ…
ตรวจตัวอย่าง 2: args ไม่ตรง schema: ✖ ตัวเลือกไม่ถูกต้อง: … → at category
ข้อ 1: product
ข้อ 2: แปลงไม่สำเร็จ
  เหตุที่ไม่ผ่าน: args ไม่ตรง schema: ✖ เกินกำหนด: string ควรมีไม่เกิน 15 ตัวอักษร → at summary
...
แปลงสำเร็จ: 3/6
```

- [ ] `ตรวจตัวอย่าง 1` มีคำว่า `ไม่ได้เรียกเครื่องมือ`
- [ ] `ตรวจตัวอย่าง 2` มีคำว่า `category`
- [ ] ทุกข้อมีบรรทัด `ข้อ i: <category>` หรือ `ข้อ i: แปลงไม่สำเร็จ` ครบข้อ 1 ถึง 6
- [ ] `แปลงสำเร็จ: N/6` เท่ากับจำนวนบรรทัด `ข้อ i: <category>`
- [ ] จำนวนบรรทัด `เหตุที่ไม่ผ่าน:` เท่ากับ 6 − N และทุกบรรทัดมีเหตุผลตามหลัง (ไม่ว่าง)

**`exercise-2.*`**

```
ตรวจตัวอย่าง: ได้ผลในครั้งที่ 2
ตรวจตัวอย่าง: ลองครบ 3 ครั้งแล้วยังไม่ได้
ข้อ 1: product (ครั้งที่ 1)
...
แปลงสำเร็จ: 6/6
```

- [ ] บรรทัด `ตรวจตัวอย่าง:` มี 2 บรรทัดพอดี: `ได้ผลในครั้งที่ 2` แล้ว `ลองครบ 3 ครั้งแล้วยังไม่ได้`
- [ ] `แปลงสำเร็จ: N/6` โดย N อย่างน้อย 5 และเท่ากับจำนวนบรรทัด `ข้อ i: <category> (ครั้งที่ k)`
- [ ] ทุกค่า k (ทั้ง `(ครั้งที่ k)` และ `ลอง k ครั้ง`) อยู่ระหว่าง 1 ถึง 3

**`exercise-3.*`** (input ที่ใช้ตรวจ: `มีเมล็ดกาแฟคั่วเข้มไหม` · `คำสั่งซื้อ O1002 ถึงไหนแล้ว` · `ขอดูคำสั่งซื้อ O1004 หน่อย` · `จบ`)

- [ ] มีบรรทัด `(ประเภท: …)` 3 บรรทัดตามลำดับ: `product`, `order O1002`, `order O1004`
- [ ] `(ข้อมูลที่ส่งให้โมเดล: …)` ของตาที่ 1 มีคำว่า `คั่วเข้ม`

## แบบฝึกหัด

1. **`exercise-1.*`:** เติม `describeFailure(raw)` ให้คืนเหตุผลบรรทัดเดียว: ถ้าไม่มี tool call คืน `ไม่ได้เรียกเครื่องมือ ตอบเป็นข้อความ: <ข้อความ 60 ตัวอักษร>` ถ้ามี tool call ให้ตรวจ args ด้วย `StrictQuestion.safeParse` แล้วคืน `args ไม่ตรง schema: <prettifyError ที่ยุบเป็นบรรทัดเดียว>` ไฟล์ใช้ schema ที่เข้มขึ้น (`summary` ยาวไม่เกิน 15 ตัวอักษร) เพื่อให้มีโอกาสเห็น args ที่ไม่ผ่านจริง และพิมพ์เหตุผลของทุกข้อ
2. **`exercise-2.*`:** เติม `classifyWithRetry(classify, message, maxAttempts)` ให้เรียก `classify(message)` ซ้ำเมื่อได้ `null` จนได้ผลหรือครบ `maxAttempts` แล้วคืน `{ result, attempts }` ไฟล์ตรวจด้วยตัวปลอม 2 ตัว (ได้ผลครั้งที่ 2 กับ ไม่ได้ผลเลย) แล้วใช้กับโมเดลจริงโดย `classify` อ่าน `parsed ?? null` จาก `includeRaw`
3. **`exercise-3.*` ⭐:** เติม `contextFor(question, customerId)` ให้ประกอบข้อมูลจากร้านตามประเภทคำถาม: `product` ค้นด้วย `keywords` ทีละคำ (ไม่ซ้ำ ไม่เกิน 5 ชิ้น), `order` เปิดคำสั่งซื้อของลูกค้าคนนี้หรือรายการคำสั่งซื้อทั้งหมด, `policy`/`other` คืน `""` ไฟล์คือแชทบอทที่แยกประเภทก่อนตอบและใส่ข้อมูลนั้นใน system ทุกตา

ไฟล์แบบฝึกมี 👉 และค่าชั่วคราวไว้ให้รันได้ แต่ผลจะยังไม่ผ่าน checklist จนกว่าจะแก้ครบ ถ้าติด เปิดไฟล์ `example.*` ข้างๆ และอ่านเฉลยบน branch `solutions` เมื่อทำเองแล้ว
