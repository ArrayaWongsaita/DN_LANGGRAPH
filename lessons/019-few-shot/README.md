# บท 019: few-shot สอนโมเดลด้วยตัวอย่าง

บางงานบอกเป็นคำสั่งอย่างเดียวแล้วโมเดลก็ทำไม่ตรงใจ เช่น ให้แยกประเภทข้อความของลูกค้า โมเดลอาจตอบยาวเป็นประโยค หรือใช้ชื่อประเภทที่เราไม่ได้กำหนด วิธีแก้ที่ง่ายที่สุดคือ **ยกตัวอย่าง** คำถามกับคำตอบที่ถูกไปพร้อมกัน บทนี้ลองแยกข้อความลูกค้าร้าน DN Shop เป็น 4 ประเภท เทียบผลเมื่อไม่มีตัวอย่าง (zero-shot) กับมีตัวอย่าง (few-shot) ใช้เวลาประมาณ 45-60 นาที ทำทั้งแบบ Ollama (`.ollama.ts`) และ Google (`.google.ts`)

## จบบทนี้แล้วทำอะไรได้

- อธิบายความต่างของ zero-shot กับ few-shot
- ส่งตัวอย่างเป็นคู่ข้อความ `user` / `assistant` ให้โมเดลเห็นรูปแบบคำตอบที่ต้องการ
- วัดผลเป็นตัวเลขด้วยชุดทดสอบ 2 ค่า: "รูปแบบถูก" (ตอบเป็นป้ายที่กำหนด) กับ "ตรงกับที่คาด" (ตอบป้ายถูกข้อ)
- เลือกตัวอย่างให้สอน "ขอบเขต" ของแต่ละประเภท และรู้ว่าห้ามเอาข้อสอบมาเป็นตัวอย่าง
- เขียนตัวอย่างเป็นข้อความต่อท้าย system แทนการส่งเป็นคู่ข้อความ

## เชื่อมกับที่รู้แล้ว

| ที่รู้แล้ว | ในบทนี้ |
|---|---|
| บท 009: ข้อความ `user` / `assistant` (หรือ `ai`) ใช้ทำ few-shot ได้ | ตัวอย่างแต่ละข้อคือข้อความ `user` (คำถาม) ตามด้วย `assistant` (คำตอบที่ถูก) |
| บท 017: system prompt บอกกฎ | บทนี้เพิ่ม "ตัวอย่าง" เป็นอีกวิธีคุมคำตอบ ใช้ร่วมกับ system ได้ |
| บท 018: ข้อมูลที่ใส่ใน prompt เปลือง token | ตัวอย่างก็เป็นข้อความที่ต้องส่งทุกครั้งที่ถาม จึงเพิ่ม token เหมือนกัน |
| TypeScript: `as const`, `flatMap` | `LABELS` เป็นรายการที่ตายตัว และ `flatMap` แตกตัวอย่าง 1 ข้อให้เป็น 2 ข้อความ |

## เนื้อหา

บทนี้ต้องผ่านบท 009 และ 017 ก่อน

### 1. งานแยกประเภท และป้ายที่เรากำหนด

ลูกค้าส่งข้อความเข้ามาหลายแบบ เราอยากแยกเป็น 4 ประเภทเพื่อส่งต่อให้ถูกที่:

| ป้าย | ความหมาย | ตัวอย่าง |
|---|---|---|
| `product` | ถามเรื่องสินค้า | `มีแก้วเก็บความเย็นไหม` |
| `order` | ถามเรื่องคำสั่งซื้อ | `ขอเลขพัสดุของคำสั่งซื้อ O1005` |
| `policy` | ถามกฎของร้าน (ค่าส่ง การคืนสินค้า) | `ค่าส่งต่างจังหวัดเท่าไร` |
| `other` | เรื่องอื่น | `แนะนำหนังสนุกๆ หน่อย` |

ไฟล์เก็บป้ายไว้ใน `LABELS = [...] as const` เพื่อให้ TypeScript รู้ว่ามีแค่ 4 ค่า และใช้ตรวจว่าโมเดลตอบอยู่ในรายการนี้ไหม system prompt คือ `แยกประเภทข้อความของลูกค้าร้าน DN Shop เป็น product, order, policy หรือ other`

### 2. zero-shot กับ few-shot

- **zero-shot:** ส่งแค่ system กับคำถาม ไม่มีตัวอย่าง โมเดลต้องเดาเองว่าตอบรูปแบบไหน อาจตอบ `คำถามนี้เกี่ยวกับสินค้า` แทน `product`
- **few-shot:** ส่งตัวอย่างไปก่อน (few แปลว่า "ไม่กี่ข้อ") ตัวอย่างแต่ละข้อเป็นคู่ข้อความ user ถาม assistant ตอบ แล้วจบด้วยคำถามจริง โมเดลเห็นว่าข้อความก่อนหน้าตอบกันอย่างไรก็ตอบตาม

ฟังก์ชัน `fewShotMessages(examples, question)` ประกอบข้อความตามลำดับ system, คู่ user/assistant ของทุกตัวอย่าง, user คำถามจริง ขั้นที่ 1 พิมพ์ผลให้ดู (ไม่ยิงเน็ต):

```
--- ขั้นที่ 1: ข้อความที่ส่งเมื่อมีตัวอย่าง ---
system: แยกประเภทข้อความของลูกค้าร้าน DN Shop เป็น product, order, policy หรือ other
user: มีแก้วเก็บความเย็นไหม
assistant: product
user: ขอเลขพัสดุของคำสั่งซื้อ O1005
assistant: order
user: ค่าส่งต่างจังหวัดเท่าไร
assistant: policy
user: แนะนำหนังสนุกๆ หน่อย
assistant: other
user: เมล็ดกาแฟคั่วอ่อนมีรสเปรี้ยวไหม
รวม 10 ข้อความ
```

(ข้อความของโมเดลที่ส่งจริงใช้รูปย่อ `{ role, content }` เหมือนบท 009 โดย `assistant` ในรูปย่อคือข้อความของโมเดล)

### 3. ตัวอย่างสอนทั้ง "รูปแบบ" และ "ขอบเขต"

ตัวอย่างสอนโมเดล 2 อย่างพร้อมกัน:

- **รูปแบบ:** ตอบคำเดียวที่เป็นป้าย ไม่ต้องอธิบาย (วัดด้วย "รูปแบบถูก")
- **ขอบเขต:** ข้อความแบบไหนเข้าประเภทไหน เช่น "แนะนำหนังสือ" คือ `other` ไม่ใช่ `product` (วัดด้วย "ตรงกับที่คาด")

ตัวอย่างต้องมีครบทุกประเภท และถ้ามีข้อความกำกวมที่มักผิด (เช่น พูดถึงสินค้าแต่จริงๆ ถามเรื่องคำสั่งซื้อ) ควรเพิ่มตัวอย่างของกรณีนั้น (ข้อ 1 ของแบบฝึกหัด)

**ห้ามใช้ข้อความในชุดทดสอบมาเป็นตัวอย่าง:** ถ้าตัวอย่างมีข้อสอบอยู่แล้ว โมเดลแค่จำคำตอบ คะแนนจะดูเก่งเกินจริง และเราไม่รู้ว่าข้อความใหม่จริงๆ จะผ่านไหม ต้องแยกชุดตัวอย่างกับชุดทดสอบออกจากกัน (แบบฝึกหัดข้อ 1 ตรวจเรื่องนี้ให้)

**ตัวอย่างมีค่าใช้จ่าย:** ตัวอย่างทุกข้อถูกส่งไปทุกครั้งที่ถาม (ตามบท 018) 4 ตัวอย่างคือ 8 ข้อความเพิ่ม ถ้ามีตัวอย่างเป็นร้อยจะเปลืองมาก เลือกตัวอย่างที่ให้ความรู้ใหม่ ไม่ซ้ำกัน

### 4. ขั้นที่ 2: วัดผลด้วยชุดทดสอบ

ชุดทดสอบ `TESTS` มี 5 ข้อความที่ไม่ซ้ำกับตัวอย่าง พร้อมประเภทที่คาด ไฟล์ถามทีละข้อ 2 รอบ (zero-shot แล้ว few-shot) และพิมพ์:

- `ข้อ i: <ป้ายที่โมเดลตอบ>` 5 บรรทัด ป้ายคือคำตอบที่ตัดช่องว่างหัวท้ายและทำเป็นตัวพิมพ์เล็กแล้ว ย่อให้เหลือบรรทัดเดียวไม่เกิน 40 ตัวอักษร (ถ้าโมเดลตอบยาวจะเห็นว่าผิดรูปแบบ)
- `รูปแบบถูก: Y/5` ตอบเป็นป้ายในรายการ `LABELS` กี่ข้อ
- `ตรงกับที่คาด: X/5` ตอบตรงกับประเภทที่คาดกี่ข้อ

สิ่งที่ควรเห็น: รอบ few-shot ควรได้รูปแบบถูก 5/5 และตรงกับที่คาดอย่างน้อย 4/5 ส่วนรอบ zero-shot ผลต่างกันตามโมเดล บางตัวตอบเป็นป้ายได้เองบ้าง บางตัวตอบเป็นประโยค (เกณฑ์ตรวจแค่ว่าตัวเลขสรุปตรงกับรายข้อ ไม่ตรวจว่าผลดีแค่ไหน ให้ดูเทียบกับรอบ few-shot)

ต่อยอด: บท 022 จะให้โมเดลแยกประเภทเป็นอ็อบเจ็กต์ที่มี type ที่ตรวจด้วย schema แทนข้อความคำเดียว

### 5. แบบฝึกหัดสองแบบ

- ข้อ 1: เพิ่มตัวอย่างสำหรับข้อความกำกวม แล้วถามข้อสอบที่ยากขึ้น (`HARD_TESTS`)
- ข้อ 2: เปลี่ยนวิธีส่งตัวอย่าง จากคู่ข้อความ เป็นข้อความต่อท้าย system (`ข้อความ: ... → ประเภท: ...` บรรทัดละข้อ) แล้วเทียบว่าผลยังดีไหม ข้อสังเกตจากการทดสอบ: ตัวอย่างที่เป็นข้อความธรรมดาสอนรูปแบบคำตอบได้อ่อนกว่าคู่ user/assistant โมเดลมักตอบเลียนแบบเป็น `ประเภท: product` ไฟล์จึงเติมประโยค `ตอบเป็นป้ายคำเดียวเท่านั้น` ไว้ท้าย system ให้แล้ว

## จุดที่มักพลาด

- **เอาข้อสอบมาเป็นตัวอย่าง:** ผลดูดีเกินจริง ต้องแยกชุด
- **ตัวอย่างไม่ครบทุกประเภท:** โมเดลไม่เคยเห็นประเภทนั้น มักไม่ตอบประเภทนั้นเลย
- **ตัวอย่างขัดกันเอง:** ข้อความคล้ายกันแต่ป้ายต่างกัน โมเดลสับสน
- **ลืมว่าตัวอย่างเพิ่ม token ทุกครั้งที่ถาม:** ตัวอย่างยิ่งมาก ยิ่งเปลืองและช้า
- **เทียบผลจากข้อเดียว:** โมเดลเปลี่ยนคำตอบได้ทุกครั้ง ดูตัวเลขรวม (X/5) ไม่ใช่ข้อเดียว
- **เขียนป้ายไม่ตรงกับ `LABELS`:** เช่นตัวอย่างตอบ `Product` แต่ `LABELS` ใช้ `product` ผลการเทียบจะผิดทั้งที่โมเดลตอบถูก (ไฟล์จึงทำป้ายเป็นตัวพิมพ์เล็กก่อนเทียบ)

## ผลที่ควรเห็น

### ขั้นที่ 1: ต้องตรงทุกตัว

ทั้ง `example.ollama` และ `example.google` พิมพ์ 12 บรรทัดตามที่แสดงในหัวข้อ 2 (หัวข้อ `--- ขั้นที่ 1: ... ---` ตามด้วยข้อความ 10 ข้อความ และบรรทัด `รวม 10 ข้อความ`)

### ขั้นที่ 2: เทียบกับ checklist

แต่ละรอบ (`--- ขั้นที่ 2: ไม่มีตัวอย่าง (zero-shot) ---` และ `--- ขั้นที่ 2: มีตัวอย่าง (few-shot) ---`) หน้าตาแบบนี้ (ป้ายและตัวเลขเปลี่ยนได้):

```
ข้อ 1: product
ข้อ 2: order
ข้อ 3: policy
ข้อ 4: other
ข้อ 5: order
รูปแบบถูก: 5/5
ตรงกับที่คาด: 5/5
```

**`example.ollama` และ `example.google`**
- [ ] ขั้นที่ 1 ตรงทั้ง 12 บรรทัด
- [ ] ทั้ง 2 รอบมี `ข้อ 1:` ถึง `ข้อ 5:` ตามลำดับ
- [ ] ตัวเลข Y ของ `รูปแบบถูก` และ X ของ `ตรงกับที่คาด` ตรงกับที่นับเองจากบรรทัดรายข้อ (ตรวจทั้ง 2 รอบ)
- [ ] รอบ few-shot ได้ `รูปแบบถูก: 5/5` และ X อย่างน้อย 4

**`exercise-1.*`**

```
ตัวอย่างทั้งหมด: N ข้อ
ตัวอย่างที่ซ้ำกับข้อสอบ: 0 ข้อ
ข้อ 1: ...
...
ข้อ 5: ...
ตรงกับที่คาด: X/5
```

- [ ] `ตัวอย่างทั้งหมด: N ข้อ` โดย N อย่างน้อย 6 (4 ข้อเดิม กับที่เพิ่มอย่างน้อย 2 ข้อ)
- [ ] `ตัวอย่างที่ซ้ำกับข้อสอบ: 0 ข้อ`
- [ ] มี `ข้อ 1:` ถึง `ข้อ 5:` ตามลำดับ
- [ ] X ตรงกับที่นับเองจากบรรทัดรายข้อ และ X อย่างน้อย 4

**`exercise-2.*`**

```
ตรวจตัวอย่าง: <examplesAsText ของ EXAMPLES 2 ข้อแรก ต่อเป็นบรรทัดเดียว>
ข้อ 1: ...
...
ข้อ 5: ...
รูปแบบถูก: Y/5
ตรงกับที่คาด: X/5
```

- [ ] บรรทัด `ตรวจตัวอย่าง:` มีข้อความและป้ายของตัวอย่าง 2 ข้อแรก (ข้อความของแต่ละข้อมีป้ายของข้อนั้นตามหลัง)
- [ ] มี `ข้อ 1:` ถึง `ข้อ 5:` ตามลำดับ
- [ ] Y และ X ตรงกับที่นับเองจากบรรทัดรายข้อ และทั้งคู่อย่างน้อย 4

> หมายเหตุ: ผลของไฟล์ `.google.ts` ในบทนี้ยังไม่ได้ทดสอบกับ key ของ Google จริง

## แบบฝึกหัด

1. **`exercise-1.*`:** เติม `moreExamples()` ให้คืนตัวอย่างเพิ่มอย่างน้อย 2 ข้อ สำหรับข้อความกำกวม (พูดถึงสินค้าแต่จริงๆ ถามเรื่องคำสั่งซื้อ หรือถามกฎของร้าน) ต้องไม่ซ้ำกับ `HARD_TESTS` ไฟล์ส่ง `[...EXAMPLES, ...moreExamples()]` แล้วถามข้อสอบ `HARD_TESTS` 5 ข้อ
2. **`exercise-2.*`:** เติม `examplesAsText(examples)` ให้เขียนตัวอย่างเป็นข้อความ บรรทัดละข้อในรูป `ข้อความ: … → ประเภท: …` ไฟล์ต่อข้อความนี้ท้าย system แล้วส่งแค่ system กับคำถาม (ไม่มีคู่ user/assistant) ถามชุด `TESTS` 5 ข้อ
