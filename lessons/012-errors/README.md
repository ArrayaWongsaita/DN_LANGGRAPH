# บท 012: อ่าน error ให้ออก

เมื่อเขียนแอปที่เรียกโมเดล error เป็นเรื่องปกติ: ลืมเปิด Ollama, ชื่อโมเดลผิด, key หมดอายุ, โควต้าเต็ม บทนี้เรียนวิธีจับ error แยกแยะว่าเป็นแบบไหน และตัดสินใจว่าควรลองใหม่หรือไม่ ใช้เวลาประมาณ 45-60 นาที ทำทั้งแบบ Ollama (`.ollama.ts`) และ Google (`.google.ts`)

## จบบทนี้แล้วทำอะไรได้

- จับ error ของการเรียกโมเดลด้วย `try/catch` โดยโปรแกรมไม่ล้มทั้งตัว
- อ่านชนิด (`name`) และเลข status ของ error ให้ออกว่าเกิดจากอะไร
- เขียน `explainError` ที่แปล error เป็นข้อความที่คนอ่านแล้วรู้ว่าต้องแก้อะไร
- ตัดสินได้ว่า error แบบไหนควรลองใหม่ (retry) แบบไหนไม่ควร
- อ่าน stack trace เพื่อหาว่า error เกิดที่บรรทัดไหนของโค้ดเรา

## เชื่อมกับที่รู้แล้ว

| ที่รู้แล้ว | ในบทนี้ |
|---|---|
| TypeScript: `try { ... } catch (e) { ... }` และ `e` เป็นชนิด `unknown` | ต้องตรวจชนิดก่อนอ่านฟิลด์ เช่น `e instanceof TypeError` |
| บท 006: ตรวจ `res.ok` และ HTTP status (404, 401, 429) | ไลบรารีโยน error ที่มีเลข status เดียวกันให้เรา อ่านได้จาก `status_code` หรือ `status` |
| บท 003-005: ลืมเปิด Ollama ได้ `fetch failed`, ชื่อโมเดลผิดได้ 404 | บทนี้ทำให้ error เหล่านี้เกิดจริงแล้วจับดู |
| บท 007: สร้างโมเดลแล้วเรียก `invoke` | `invoke` คือจุดที่ error โผล่ ไม่ใช่ตอนสร้างโมเดล |

## เนื้อหา

บทนี้ต้องผ่านบท 003 หรือ 004 (ไฟล์ `.ollama.ts`) และบท 005 (ไฟล์ `.google.ts`) ก่อน

### 1. error มี 2 แบบหลักๆ

| แบบ | เกิดเมื่อ | หน้าตา |
|---|---|---|
| **ต่อไม่ติดเลย** | Ollama ยังไม่เปิด, URL ผิด, เน็ตหลุด | `TypeError: fetch failed` ไม่มีเลข status เพราะยังไม่ได้คุยกับเซิร์ฟเวอร์ |
| **เซิร์ฟเวอร์ตอบว่าไม่ได้** | ชื่อโมเดลผิด, key ผิด, เรียกถี่เกิน, ฝั่งเซิร์ฟเวอร์พัง | error ที่มีเลข status เช่น 404, 401, 429, 500 |

เลข status ที่ต้องรู้ (เหมือนบท 006):

| status | ความหมาย | แก้อย่างไร |
|---|---|---|
| 404 | ไม่พบโมเดล | เทียบชื่อใน `.env` กับ `ollama list` (หรือชื่อรุ่นของ Gemini) |
| 401 | key ผิดหรือหมดอายุ | ตรวจ key ใน `.env` |
| 429 | เรียกถี่เกินหรือโควต้าหมด | รอแล้วลองใหม่ (บท 013 สอนวิธีจัดการ) |
| 500 ขึ้นไป | ฝั่งเซิร์ฟเวอร์มีปัญหา | มักหายเองถ้ารอสักพัก |

### 2. อ่านเลข status จาก error

ในบล็อก `catch (e)` ตัวแปร `e` เป็น `unknown` อ่านฟิลด์ตรงๆ ไม่ได้ ต้องตรวจก่อน (ไฟล์ตัวอย่างห่อไว้ในฟังก์ชัน `statusOf`):

```ts
function statusOf(e: unknown): number | undefined {
  if (typeof e !== "object" || e === null) return undefined;
  const fields = e as Record<string, unknown>;
  const status = fields.status_code ?? fields.status;
  return typeof status === "number" ? status : undefined;
}
```

- `ChatOllama` โยน error ที่เก็บเลขใน `status_code` ส่วนไลบรารีอื่นอาจใช้ `status` จึงอ่านทั้งสองชื่อ (`??` เลือกอันแรกที่ไม่ใช่ `undefined`)
- ถ้าไม่มีเลข status คืน `undefined` และเราดูต่อที่ชนิดของ error ด้วย `e instanceof TypeError`

### 3. explainError: แปล error เป็นข้อความที่คนอ่านรู้เรื่อง

```ts
function explainError(e: unknown): string {
  const status = statusOf(e);
  if (status === 404) return "ไม่พบโมเดล ...";
  // ... แยกกรณีอื่นต่อไป แล้วมีทางออกสุดท้ายสำหรับ error ที่ไม่รู้จัก
}
```

หลักคิดคือดูเลข status ก่อน แล้วค่อยดูชนิดของ error และต้องมีทางออกสุดท้ายสำหรับ error ที่ไม่รู้จัก (ไฟล์ตัวอย่างเขียนครบทุกกรณีให้ดู) ขั้นที่ 1 ของไฟล์ตัวอย่างลองกับ error ปลอม 4 ตัว (ไม่ยิงเน็ต) เพื่อให้เห็นว่าฟังก์ชันทำงานอย่างไรก่อนเจอของจริง

### 4. ทำให้ error เกิดจริงและจับด้วย try/catch

ขั้นที่ 2 ทำให้เกิด error จริงทีละสถานการณ์ แต่ละสถานการณ์ห่อด้วย `try/catch` โปรแกรมจึงไม่ล้ม และจบด้วย exit 0 ทุกกรณี:

**ฝั่ง Ollama (4 สถานการณ์)**

1. `ต่อ Ollama ไม่ได้`: ตั้ง `baseUrl: "http://127.0.0.1:9"` (พอร์ต 9 ไม่มีโปรแกรมไหนเปิดรอ) ได้ `TypeError: fetch failed`
2. `ชื่อโมเดลผิด`: เอาชื่อใน `.env` ต่อท้ายด้วย `-not-real` ได้ status 404
3. `key ผิด`: ทดลองได้เฉพาะตอนต่อ Ollama Cloud ตรง (`OLLAMA_BASE_URL=https://ollama.com`) โดยส่ง `Authorization: Bearer wrong-key-for-lesson-012` ได้ 401 ถ้าใช้ Ollama ในเครื่อง ไฟล์จะพิมพ์ `ข้าม: ...` แทน (ในเครื่องไม่มี key ให้ผิด)
4. `ตั้งค่าถูกต้อง`: ใช้ค่าจาก `.env` ตามปกติ ต้องได้คำตอบกลับมา

**ฝั่ง Google (3 สถานการณ์)**

1. `ชื่อโมเดลผิด`: `GOOGLE_MODEL` ต่อท้ายด้วย `-not-real`
2. `key ผิด`: ส่ง `apiKey: "wrong-key-for-lesson-012"`
3. `ตั้งค่าถูกต้อง`

ทุกสถานการณ์ที่เกิด error พิมพ์ 4 บรรทัด (เยื้อง 2 ช่อง): `ชนิด` (`e.name`), `status` (เลข หรือ `-` ถ้าไม่มี), `ข้อความ` (บรรทัดแรกของ `e.message`) และ `อธิบาย` (ผลของ `explainError`) ข้อความของ error อาจยาวหลายบรรทัด จึงเอาแค่บรรทัดแรก

### 5. ควรลองใหม่ (retry) หรือไม่

| error | ลองใหม่ได้ไหม | เพราะ |
|---|---|---|
| ต่อไม่ติด (`TypeError`) | ได้ | เน็ตสะดุดหรือ Ollama เพิ่งเปิด อาจหายเอง |
| 429 | ได้ (รอก่อน) | เป็นเรื่องช่วงเวลา รอแล้วโควต้าคืน |
| 500 ขึ้นไป | ได้ | ฝั่งเซิร์ฟเวอร์ชั่วคราว |
| 404, 401 | ไม่ได้ | ลองกี่ครั้งก็ผิดเหมือนเดิม ต้องแก้ค่าใน `.env` |

การลองซ้ำกับ error ที่ไม่มีวันหายเสียเวลาและโควต้าเปล่า แบบฝึกข้อ 2 ให้เขียนฟังก์ชันตัดสินเรื่องนี้ (บท 013 จะเอาไปใช้จริง)

### 6. error เมื่อโมเดลไม่รองรับ tools

บางรุ่นไม่รองรับการเรียก tool (บท 023-024) ถ้าเอาไปผูก tool จะได้ error บอกว่าโมเดลนั้นไม่รองรับ tools เรื่องนี้อธิบายในบทนี้เป็นความรู้ล่วงหน้า ไม่มีไฟล์ให้ทดลอง: เจอแล้วให้เปลี่ยนไปใช้รุ่นที่รองรับ TODO(6b): ข้อความ error จริง

### 7. วิธีอ่าน stack trace

ถ้าไม่ได้ `catch` error ไว้ โปรแกรมจะล้มและพิมพ์ stack trace หน้าตาประมาณนี้:

```
TypeError: fetch failed
    at node:internal/deps/undici/undici:...
    at async ChatOllama._streamResponseChunks (...)
    at async main (/.../lessons/012-errors/example.ollama.ts:70:5)
```

- **บรรทัดแรก** คือชนิดและข้อความของ error อ่านบรรทัดนี้ก่อนเสมอ
- **บรรทัดที่ขึ้นต้น `at`** คือลำดับการเรียกฟังก์ชัน จากจุดที่เกิดปัญหา (บนสุด) ย้อนขึ้นไปหาจุดเริ่ม (ล่างสุด)
- บรรทัดส่วนใหญ่อยู่ในไลบรารี (`node:internal` หรือ `node_modules`) ให้มองหาบรรทัดแรกที่เป็นไฟล์ของเรา (เช่น `lessons/...`) พร้อมเลขบรรทัดและเลขคอลัมน์ นั่นคือจุดในโค้ดเราที่เรียกไลบรารีแล้วพัง
- `e.cause` (ถ้ามี) เก็บ error ต้นเหตุที่อยู่ลึกกว่า เช่น เหตุผลที่ `fetch failed`

## จุดที่มักพลาด

- **ลองอ่าน `e.status` โดยไม่ตรวจชนิด:** `e` เป็น `unknown` TypeScript ไม่ยอม และบางไลบรารีใช้ `status_code` จึงอ่านทั้งสองชื่อ
- **ใช้แต่ `e.message` ตัดสิน:** ข้อความเปลี่ยนตามเวอร์ชันไลบรารีและภาษา ใช้ชนิดและเลข status ตัดสินจะเชื่อถือได้กว่า
- **`catch` แล้วเงียบ:** ต้องพิมพ์หรือบันทึกอะไรสักอย่างเสมอ ไม่เช่นนั้นหาสาเหตุไม่เจอ
- **ลองใหม่กับ 404 หรือ 401:** ไม่มีวันหาย ต้องแก้ค่าที่ผิด
- **ลองใหม่ทันทีรัวๆ กับ 429:** ยิ่งทำให้โควต้าเต็มเร็วขึ้น ต้องรอก่อน (บท 013)
- **พิมพ์ error ทั้งก้อนลง log:** error บางชนิดมี header ที่มี key ปนอยู่ พิมพ์เฉพาะที่จำเป็น ห้ามเอา key ใส่ในโค้ดหรือรายงาน
- **ใช้ key ปลอมแล้วเจอผลต่างจากที่อธิบาย:** บาง provider ตอบ 400 แทน 401 เมื่อ key รูปแบบผิด เลขจริงอาจต่างกัน ดูผลที่ได้จากไฟล์ตัวอย่างเป็นหลัก


## แบบฝึกหัด

1. **`exercise-1.*`:** เติม `explainError(e)` ให้คืนข้อความภาษาไทยที่อธิบาย error (ไฟล์มี `statusOf` ให้ใช้แล้ว) แล้วไฟล์จะทำให้เกิด error จริง 2 สถานการณ์ (Ollama: ต่อไม่ได้ กับชื่อโมเดลผิด, Google: ชื่อโมเดลผิด กับ key ผิด) ไฟล์ Google มีสถานการณ์ 3 เป็น error ปลอม status 429 เพิ่ม และพิมพ์ `อธิบาย: ...` ของแต่ละสถานการณ์ โดยแต่ละชนิด error ควรได้คำอธิบายต่างกัน
2. **`exercise-2.*`:** เติม `isRetryable(e)` ให้คืน `true` เมื่อเป็น `TypeError` หรือ status 429 หรือ status 500 ขึ้นไป ไม่เช่นนั้น `false` แล้วไฟล์จะพิมพ์ `ควรลองใหม่: ใช่` หรือ `ไม่ใช่` ของ 2 สถานการณ์เดียวกัน และสถานการณ์ 3 ที่เป็น error ปลอมมี status 429 (ต้องได้ `ใช่`)

ไฟล์แบบฝึกมี 👉 และค่าชั่วคราวไว้ให้รันได้ แต่ผลจะยังไม่ผ่าน checklist จนกว่าจะแก้ครบ ถ้าติด เปิดไฟล์ `example.*` ข้างๆ และอ่านเฉลยบน branch `solutions` เมื่อทำเองแล้ว
